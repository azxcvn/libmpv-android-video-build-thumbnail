# 同步上游更新 + 重新打补丁 操作指南

> 这份文档是给「另一个 AI」或「未来的自己」看的执行手册。目标很明确:
>
> 1. 上游 [Predidit/libmpv-android-video-build](https://github.com/Predidit/libmpv-android-video-build)
>    发布了新提交,要把它的更新同步进本项目 `libmpv-android-video-build-main/`。
> 2. 同步之后,确保本项目自己的补丁(尤其是 mpv 缩略图补丁 `mk_thumbnail.patch`)
>    仍然能干净地应用、正常编译。
>
> 全程 **不设置 git upstream remote、不做 git merge**。用自己的文件内容 diff 来对齐。

---

## 背景:为什么不能直接 merge

本项目 `libmpv-android-video-build-main/` 最初是「下载 zip → 解压 → git init →
一次性提交」得到的。它的第一个提交 `9db2ead` 是一个没有父提交的完整快照,
和 Predidit 的 git 历史 **没有共同祖先**。

因此,如果直接 `git remote add upstream ... && git merge upstream/main`,
会产生大量毫无意义的冲突。**放弃 merge 路线**,改用「以文件内容为基准的 diff 同步」。

---

## 项目里哪些东西是不能动的(自己的资产)

同步时,**永远不要覆盖**下面这些是本项目自己加的、Predidit 里没有的内容:

- `buildscripts/patches/mpv/mk_thumbnail.patch` —— 本项目核心补丁(缩略图)
- `buildscripts/patches/mpv/mpv_fence_leak-fix.patch`(如为本项目自加)
- `DOCS/` 整个目录
- 仓库根目录的 `_gen_patch.ps1`、`_patch_stage/`、`_apply_test/`(本地辅助工具,均未提交进 git 也可以保留)
- 任何你自己写的脚本 / 文档

判断标准很简单:**Predidit 仓库里没有、而本项目里有**的文件,默认是"自己的资产",不要被同步动作覆盖。

---

## 第一步:准备一份最新的 Predidit 副本(临时,用完可删)

在**项目目录之外**的临时位置 clone 一份(into a temp dir),这**不是设置上游**:

```bash
git clone https://github.com/Predidit/libmpv-android-video-build.git /tmp/predidit
cd /tmp/predidit
git log -1 --oneline        # 记录下当前最新 commit,便于日后对照
```

如果已经有 `/tmp/predidit`,更新它:

```bash
cd /tmp/predidit
git fetch origin
git checkout main
git pull --ff-only
```

---

## 第二步:目录级 diff,找出 Predidit 改了哪些地方

只对比「项目内容目录」,忽略 `.git`。重点目录:

- `buildscripts/`
- `.github/`
- `build.gradle.kts`
- `settings.gradle.kts`
- `gradle/`
- `gradlew`

用 `diff -ru` 做递归对比(把所有差异写出,再人工判断):

```bash
diff -ru \
  /tmp/predidit/buildscripts \
  ~/Desktop/jartest/libmpv-android-video-build-main/buildscripts \
  > /tmp/diff_buildscripts.txt

diff -ru \
  /tmp/predidit/.github \
  ~/Desktop/jartest/libmpv-android-video-build-main/.github \
  > /tmp/diff_github.txt

# 逐文件单独对比也很直观,例如核心的依赖版本文件:
diff -u \
  /tmp/predidit/buildscripts/include/depinfo.sh \
  ~/Desktop/jartest/libmpv-android-video-build-main/buildscripts/include/depinfo.sh
```

解读 diff 时的要点:

- `diff -ru A B` 里的 `A` 是 Predidit(上游),`B` 是本项目。
- 输出中 `-` 开头是 Predidit 有、本项目没有(可能是它新增/它改了)。
- 输出中 `+` 开头是本项目有、Predidit 没有(可能本项目自己加的,**不要误删**)。
- 如果某一组文件只在「本项目」里多出,那多半是本项目的自有资产,跳过。

---

## 第三步:只把「你想要的更新」复制过来

Predidit 的更新大多是这几类,都很小、可手动抄:

1. `buildscripts/include/depinfo.sh` —— 依赖版本号 bump(最频繁的一种)。
2. `buildscripts/scripts/*.sh` —— 某个依赖的构建脚本改动。
3. `buildscripts/patches/**` —— 某个依赖的补丁改动。
4. `.github/workflows/build.yaml` —— CI 流程改动。
5. `build.gradle.kts` / `gradle/**` —— Gradle 配置改动。

**操作建议**:逐类看 diff,只把你**确实需要追**的改动,用编辑器手动改到本项目对应文件里。
保持「最小同步」,不盲目整目录覆盖。这样最安全,也最符合"不用上游"的诉求。

> 如果你确实想一次性对齐某个纯上游目录(里面没有任何本项目自有文件),
> 可以整目录覆盖,例如:
>
> ```bash
> rsync -av --delete /tmp/predidit/buildscripts/flavors/ \
>   ~/Desktop/jartest/libmpv-android-video-build-main/buildscripts/flavors/
> ```
>
> 但在覆盖前,务必先用上面的 diff 确认该目录里没有本项目的自有改动。

## 第四步:同步之后,重新打上本项目自己的补丁

本项目的补丁**不是** commit 进源码的,而是 **CI/构建时自动 `git apply`** 的。
入口在 `buildscripts/patch.sh`:

```bash
for dep_path in patches/*; do
    dep=$(echo $dep_path | cut -d/ -f 2)   # 例如 mpv、ffmpeg、libplacebo
    cd deps/$dep
    git reset --hard                        # 先把上游源码还原干净
    for patch in patches/*; do              # 再逐条打补丁
        git apply "$ROOT/$patch"
    done
done
```

所以「重新打补丁」的本质是:**确认每个 `.patch` 都能在新版源码上 `git apply` 成功**。

### 4.1 先判断:mpv 版本有没有变?

最关键的一步 —— 看 `v_mpv`:

```bash
grep '^v_mpv=' buildscripts/include/depinfo.sh
grep '^v_ffmpeg=' buildscripts/include/depinfo.sh
grep '^v_libplacebo=' buildscripts/include/depinfo.sh
```

分两种情况:

#### 情况 A:`v_mpv`(以及 ffmpeg/libplacebo 等)都没变

→ 你的补丁**无需重打**,原样有效。同步完 Predidit 的其它改动后,直接提交即可。

#### 情况 B:`v_mpv` 变了(如从 `32a164cc...` 换成了新 commit)

→ `mk_thumbnail.patch` 很可能对不上新 mpv 源码(mpv 的目录结构、`meson.build`
会随版本变化),**必须重新生成缩略图补丁**。继续看 4.2。

### 4.2 重新生成 mpv 缩略图补丁

用项目根目录的 `_gen_patch.ps1`:

```powershell
# 1. 打开 _gen_patch.ps1,把顶部的 $sha 改成新的 mpv commit
#    $sha = '新的mpv commit 哈希'

# 2. 执行
pwsh ./_gen_patch.ps1
```

脚本会:

1. 从 mpv 上游拉取新 commit 的 `include/mpv/client.h` 和 `meson.build`;
2. 从旧的 `mk_thumbnail.patch` 里提取缩略图声明和 `thumbnail.c` 实现;
3. 用新源码重新生成 `buildscripts/patches/mpv/mk_thumbnail.patch`。

### 4.3 验证补丁能干净应用(必须做,不能省)

本地无法跑完整交叉编译也没关系,至少要验证 **`git apply` 不报错**。

在能跑 shell 的环境(或 CI 里)执行:

```bash
cd buildscripts
./patch.sh
```

如果输出只有 `Applying ...`、没有 `error:` / `patch does not apply`,
说明补丁还都干净。出现 reject 就去按新源码调整 `mk_thumbnail.patch`
(重跑 `_gen_patch.ps1` 或手工微调)。

### 4.4 提交并推送

```bash
cd ~/Desktop/jartest/libmpv-android-video-build-main
git add -A
git status                          # 检查:自有资产没被误删
git commit -m "sync: 同步 Predidit 上游更新 + 重新生成缩略图补丁"
git push origin main
```

推送后,CI 会自动触发 `build.yaml`,产出新的 `*.jar`。

## 附录:一次完整同步的速查清单

- [ ] `git clone`(或 `pull`)最新 Predidit 到 `/tmp/predidit`
- [ ] `diff -ru` 对比 `buildscripts/`、`.github/`、`build.gradle.kts` 等目录
- [ ] 逐个判断差异,只手动抄入「确实要追」的更新
- [ ] 确认没有覆盖本项目自有文件(`mk_thumbnail.patch`、`DOCS/` 等)
- [ ] 检查 `depinfo.sh` 的 `v_mpv` 等版本号是否变化
- [ ] 若 `v_mpv` 变了 → 改 `_gen_patch.ps1` 的 `$sha` → 跑脚本重新生成补丁
- [ ] 跑 `buildscripts/patch.sh` 验证 `git apply` 无冲突
- [ ] `git status` 复核 → commit → push
- [ ] 在 GitHub 上确认 CI 构建产物正常

---

## 附:关键文件速查

| 文件 | 作用 |
| --- | --- |
| `buildscripts/include/depinfo.sh` | 所有依赖的版本号(mpv、ffmpeg、libplacebo 等),同步时重点看这里 |
| `buildscripts/patch.sh` | 编译前把 `patches/**` 自动 `git apply` 到各依赖源码 |
| `buildscripts/patches/mpv/mk_thumbnail.patch` | 本项目核心:mpv 缩略图功能补丁(自有资产) |
| `_gen_patch.ps1` | 重新生成 `mk_thumbnail.patch` 的脚本(同步后 mpv 版本变了就靠它) |
| `.github/workflows/build.yaml` | CI 流程,产出 `*.jar` |
| `DOCS/README.md` | 项目说明与上游关系 |

---

> 特别提醒(给执行者):**同步 = 拉进来 Predidit 的新东西,不等于覆盖本项目的自有改动。**
> 任何时候拿不准一个文件是本项目自己的还是上游的,先 `diff` 看两边 `+`/`-`,
> 而不是直接覆盖。宁可少同步,不可误删自己的补丁与文档。
